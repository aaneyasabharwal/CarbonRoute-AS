# Global zone catalogue

CarbonRoute supports **every electricity-grid zone in the Electricity Maps public zone list: 351
zones in 207 countries on all inhabited continents** (catalogue version 2026-11-14). There is no
selector limit and no hidden subset. What is known about each zone's *data* is kept separate from
its presence in the catalogue.

## 1. Contents and counts

| Count | Value |
|---|---|
| Zones | **351** (13 are aggregates of sub-zones, e.g. `US`, `IN`, `AU`) |
| Countries / territories | 207 |
| Continents (UN M49) | Africa 56, Americas 121, Asia 71, Europe 80, Oceania 23 |
| With an IANA time zone | **346** |
| Without a time zone (deliberately) | 5 aggregates spanning several time zones: `US`, `CA`, `BR`, `AU`, `MY` (times shown in UTC) |
| Flagged entries (documented below) | 14 |

Per zone: id, name, country, continent and UN M49 area (e.g. *Americas · South America*,
*Asia · Western Asia*), IANA time zone and its source, parent and sub-zones, provider tier and
commercial availability, and four separate availability facts:

| Availability fact | Zones | Evidence |
|---|---|---|
| In the verified catalogue | 351 | provider's public zone list, 2026-11-14 |
| Carbon-intensity forecast / 24 h history / latest **listed by the provider** for the project's trial key | 351 / 351 / 351 | provider listing 2026-11-13. **A listing is not proof**: on 2026-11-12 the listed past-range endpoint was refused (401). |
| Live data **verified** (actually read with the project key) | **7**: DE, FR, GB, IN, IN-NO, IN-SO, US-CAL-CISO | probe log 2026-11-12 and the research collector since 2026-11-13 |
| **Own synthetic demo** profile (not real data) | 4: DE, IN-NO, US-CAL-CISO, US-TEX-ERCO (+ the synthetic `BENCHMARK-RESEARCH` trace, which is not a real zone) | `backend/src/services/carbonService.ts` |
| Demo scheduling possible | **all 351** (P13): the other 347 use the **generic synthetic trace**, the same synthetic curve for every zone without its own profile, labelled "not <zone> data" | `carbonService.ts`, `syntheticTrace` field |

## 2. Sources and licences

All sources are versioned in `data/zones/sources/`; the catalogue is generated by
`node scripts/zones/build-zone-catalogue.mjs` (no network, no key, no provider quota) into
`backend/src/carbon/zoneCatalogue.generated.ts`. CI rebuilds it and fails if the result differs.

## 3. Time zones: rules and the 14 flagged entries

1. Take the zone's time zone from the provider's configuration.
2. Map legacy names with the IANA `backward` file **only if** the name is not itself listed in
   `zone.tab` (e.g. `US/Central -> America/Chicago`; `Europe/Oslo` is kept).
3. If the result is not one of the country's IANA zones and the country has exactly one, use that
   zone and record the correction. Corrected (provider configuration said ... ):
   `BA` Asia/Bahrain -> **Europe/Sarajevo**; `GF` Europe/Paris -> **America/Cayenne**;
   `MQ` Europe/Paris -> **America/Martinique**; `GP` America/Puerto_Rico -> **America/Guadeloupe**;
   `HR` Europe/Belgrade -> **Europe/Zagreb**; `LU` Europe/Brussels -> **Europe/Luxembourg**;
   `ZM` Africa/Maputo -> **Africa/Lusaka**.
4. An aggregate whose country has several IANA zones has no single local time: `US`, `CA`, `BR`,
   `AU`, `MY` are left **unresolved** and shown in UTC (never guessed).
5. `XK` (Kosovo) and `TW` (Taiwan) have no UN M49 entry in the dataset; their continent comes from
   the provider's region field (flagged).

Time zones are used only to *display* local times. All scheduling is done in UTC on the
provider's hourly timestamps, so daylight-saving changes cannot shift a window (tested:
`backend/test/scheduling/globalZones.test.ts`, US Pacific DST end 2026-11-01).

## 4. In the application

- `GET /api/carbon/catalogue` (public, static, rate limited, no provider call) returns the
  catalogue, its sources and counts, and `liveConfigured` for this server.
- The Prototype page's **zone selector** lists every zone, grouped by continent and area, with
  search (id, name, country, continent, area) and filters (continent; live verified; synthetic demo).
  A panel shows the availability facts for the selected zone and whether it can be scheduled in
  the chosen data mode on this server, with the reason when it cannot. Evaluate is then disabled
  and no request is made.
- **Every zone works on demo data, never silently** (P13): a zone without its own synthetic profile
  uses the generic synthetic trace, stated in the forecast title ("<zone> — generic synthetic trace … not <zone> data"), in
  the availability panel and in the API (`syntheticTrace: "generic"`); the zone keeps its own id and
  time zone. (Before P11 such zones silently received the `BENCHMARK-RESEARCH` trace under its name;
  P11 refused them; P13 allows them with the label.) A zone outside the catalogue is refused (422).
- Live scheduling for any listed zone works on a server with a valid key; a provider refusal is
  shown as an error, never replaced by other data.

## 5. Updating the catalogue

1. Save a new `GET https://api.electricitymap.org/v3/zones` response as
   `data/zones/sources/electricitymaps-zones-<date>.json` (no key needed) and update the file name in
   the build script.
2. Refresh `electricitymaps-contrib-zone-fields-<sha>.json` for new zones (only `timezone` and
   `region` fields), `iana-zone.tab` and `iana-backward`.
3. Run `node scripts/zones/build-zone-catalogue.mjs`, review the counts and flags, and update the
   `VERIFIED` list only with new evidence (zones actually read with a key).
